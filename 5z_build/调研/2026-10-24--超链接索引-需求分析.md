## 0. 结论摘要（TL;DR）

**可行，且改动面清楚；难点不在"加 `<a>`"，而在三件前置工作。** 现状是：正文页由 Word 导出 HTML 原样搬运而来，**全站正文内链 0 条、锚点 id 0 个**，所以要做这个需求，必须先建"锚点基建"，再做"关键词索引 + 自动加链"。

| 判断项 | 结论 |
|---|---|
| 技术路线 | **构建期静态注入**（`build.mjs` 里完成），不要运行期 JS linkify、也不要边缘 Function 改写（理由见 §4） |
| 词条家底 | 9 类 **5,014** 个词条；目标页 **449** 个（其中 **197** 页一页多词条、需要锚点）；职业/种族/子职 264 个词条是"一页一词条"，跳到页顶即可 |
| 正文命中量 | 最长匹配、不重叠的全站命中 **71,153 处**；「每页每词条只链首次」**30,984 处**；再要求「名字 ≥3 字」**23,516 处** |
| 推荐默认策略 | **≥3 字 + 每页首现 + 跳过脏页** ≈ **21,100–23,500 条链接**，HTML 增量约 **+1.4–1.6 MB**（正文 HTML 共 131 MB，约 +1%） |
| 锚点可行性 | run 级样式判定直接覆盖：法术 100% / 战技 100% / 魔法物品 100% / 程序 99.6% / 怪物 97.5% / 专长 90.9%（其中正文页专长 646/646=100%，缺口全在"种族专长"数据）；需要"兜底清单"的仅 **91 条**（§3.2、§3.4） |
| 最大风险 | **误链**（2 字名/通用词/同名），其次是数据脏（18 个法术名、40 个专长名、9 个 1 字名）和缓存（`body.css` 没带版本号，见 §7 R4） |
| 工作量 | P0 锚点基建 **0.5–1 天**；P1 正文互链 **1.5–2.5 天**；P2 词典深链/索引页/术语 **2–3 天**（P0 可单独上线，立刻改善现有「规则书原文」链接） |
| 建议分期 | **P0 先做**（低风险、独立价值）；P1 做核心需求；P2 看用户对"索引页 / 词典深链 / 规则术语"的取舍 |

> 一句话建议：**先把 P0 锚点做掉**（它同时修好词典"规则书原文"只能跳页顶的老问题），**P1 先只做法术/战技/程序三类**（≈15.1k 条链），跑一轮线上误链抽检后再扩到专长/魔法物品/怪物。

## 1. 需求拆解

把原话拆成 5 个可执行要素：

1. **载体**：网页版规则书正文（不是词典页、不是车卡器）。
2. **对象**：正文里的"规则关键词"，例：法术名字。
3. **动作**：自动识别这些词并标成超链接。
4. **目标**：点击后跳转到"对应词条"。
5. **索引**：需求名"超链接索引"——即一张"关键词 → 词条位置"的映射表；是否额外要一个**书后索引式的索引页**，需用户确认（§9 Q5）。

### 1.1 "对应词条"的两种解释（关键分歧）

| 解释 | 跳转目标 | 现状 | 评价 |
|---|---|---|---|
| **A. 规则书词条**（推荐） | 正文页内的锚点，例如 `法术/法术详述/3环.htm#kw-火球术` | 现在**没有锚点**，需新建 | 不离开阅读上下文；规则书本来就是词条的"正本"；锚点基建顺手修好词典原文链接 |
| B. 词典词条 | `dict.html` 里该词条的详情卡 | 词典是纯前端，**没有深链**（无 hash/query 状态）；Picker 组件有 `state.sel` 可复用 | 界面更"结构化"，但会离开阅读流；需额外做词典深链（P2） |

**推荐默认 A，P2 再补 B**：正文内链一律跳规则书词条（原位跳转），词典条目里的"原文"链接升级为精确锚点；P2 再给词典加深链、并可在词条里加"在词典中查看"入口。

### 1.2 使用场景（决定"值不值得做"）

- 读「法术规则」「职业特性」「专长描述」时看到另一个法术/战技名 → 点开看完整描述，不用去侧栏翻 3~4 层目录。
- 读某个法术描述时看到另一个法术（例：加速术的正文提到"迅捷"系法术）→ 同页内锚点跳转。
- 读怪物特性时看到它"天生施法：火球术" → 跳到火球术词条（怪物页 → 法术页）。
- 词典里点"📖 规则书原文" → 精确落到该词条（**现状只到页顶**，3环页有 155 个法术，等于没定位）。

## 2. 现状盘点（全部为实测）

### 2.1 站点结构

- 壳页面 `index.html`：左侧目录树 + 全站搜索 + iframe 正文（`5z_build/shell.html:60`，`src="__DEFAULT_PAGE__"`）。
- 正文页 = `5z_src/`（CHM 用 `hh.exe -decompile` 反编译得到）里的 Word 导出 HTML，`build.mjs` 第 4 步（355–407 行）逐页复制到 `5z_web/`，只做三处加工：注入导航条 + `<link rel="stylesheet" href="assets/body.css">`（363 行，**注意没有 `?v=` 版本号**）+ 页内搜索脚本。
- 目录页 **674** 个（hhc），磁盘 htm **662** 个，构建产物 htm 684 个；正文文字总量 **3,958,943 字**，但 HTML 体积 **131 MB**（Word 导出内联样式极重，HTML/文字比约 33:1）。
- 跳转由 `app.js` 控制：`openPage()` 设 `frame.src`（140–146 行）；`iframe.onload`（548–566 行）从 iframe URL 反推相对路径 → 更新目录高亮/面包屑。**这段逻辑只 `split('?')[0]`、没有剥掉 `#fragment`**（见 §3.6、R5）。

### 2.2 内链与锚点现状：**零**

| 指标 | 实测 |
|---|---|
| 全部 662 个源页里的 `<a>` 标签 | **20 条**：13 条外链（萌娘百科/百度百科/dndbeyond 等）+ 3 条附件链接（`5z角色卡空白模板.docx` 等）+ 4 条页内 `#锚点` |
| 4 条 `#锚点` 是否可用 | **不可用**：源页里 `id=` 0 个、Word 书签 `<a name=>` 0 个，这 4 条全是坏链（`召唤物.htm` 的 `#束缚_phb` 等） |
| 正文页里的 `id=` 属性 | **0 个** |
| 目录树能跳到的粒度 | 页面级（674 页）；无任何词条级定位 |

→ **结论：本需求是"从 0 建锚点 + 从 0 建内链"，不是"给已有链接补样式"。**

### 2.4 词典与搜索：两个"以为有其实没有"的坑

- **词典**（`dict.html`）已有全部 5,014 条，且详情页有「📖 规则书原文 →」（`5z_build/assets/dict.js` 267/289/317/379/443/551 行），但链接就是 `url` 字段——**落在目标页页顶**。3环页 155 个法术全都指向同一个页顶，等于没定位。
- **CHM 自带 hhk 索引不是关键词索引**：657 条，唯一目标 657 个，**基本等于页面清单**（hhc 674 页）；与词条名重合仅 259 个（39%），且全部指向"页"而不是"条目"。→ 不能直接拿来当"超链接索引"的数据源，关键词源必须用 `card-data`。
- **全站搜索索引**（`assets/search-index.json`，约 10 MB）是页面级倒排（BM25），只到页，无条目标题/锚点。**本需求不需要动它**（见 §3.6）。

### 2.5 发布链路

`一键更新.bat` → `update.mjs`：反编译 → `build.mjs` → `check-links.mjs`（坏链即中止）→ `verify-complete.mjs`（四向核对）→ `sync-web.mjs`（镜像到仓库根）→ git commit → push →（可选）Cloudflare 部署/purge。
→ **新功能的门禁可以挂在这三个脚本里**；HTML 走 Cloudflare Function 的 no-cache，正文页更新可立即生效；`assets/*` 走 `_headers` 长缓存（**这正是 body.css 必须带版本号的原因**）。

## 3. 关键实测结论（决定方案怎么选）

### 3.1 链接量：三种密度策略

| 策略 | 链接数 | 估算 HTML 增量 | 说明 |
|---|---|---|---|
| A 全部命中（每处都链） | 70,417 | +4.70 MB | 同一词在一页出现 N 次就链 N 次，噪声大 |
| B 每页每词条只链首次 | 30,984 | +2.07 MB | 常规 wiki 做法 |
| C 仅 ≥3 字名（每处） | 42,117 | +2.81 MB | 2 字名占 496 个，是误链重灾区 |
| **D ≥3 字 + 每页首现** | **23,516** | **+1.57 MB** | 推荐基线 |
| E D + 跳过脏页 | 21,149 | +1.41 MB | 推荐默认值（脏页见 §3.5） |
| **G D + 排除脏词条名** | **23,463** | **+1.57 MB** | 推荐默认值（排除 1 字名/整段名） |

> **推荐默认 = E + G 叠加：≥3 字 + 每页首现 + 跳过脏页 + 排除脏名 ≈ 21.1k 链、约 +1.4 MB。**

分目录看（按每页首现）：法术 15,316（563 页）、专长 3,517（489 页）、魔法物品 3,923（447 页）、怪物 2,620（588 页）、子职 2,346（559 页）、职业 1,161（479 页）、战技 1,049（255 页）、种族 784（320 页）、程序 560（110 页）。
**只看法术/战技/程序三类 = 16,877 处（每页首现），其中 ≥3 字约 15.1k 处**——这就是"第一版最小可用范围"。

接收链接的页面 650/662，**中位每页 24 条**、平均 47.7 条。长页（环位页/魔法物品页）确实会一屏十几个虚下划线，但这是"词条密度"决定的；可用低干扰样式（§5.8）。

### 3.2 锚点可行性：Word 导出结构可以稳定定位，**但必须按 run 级样式判定**

源页没有 `<h1>`/锚点，标题靠"段落 + 文字样式"表达（`parse-card-data.mjs` 的 `parsePage()` 就是按这个口径解析的）：

| 类别 | 标题样式 | 锚点定位覆盖率 |
|---|---|---|
| 法术 | 12pt 加粗 + 深红 `rgb(128,0,0)` | **1196/1196 = 100%** |
| 战技 | 加粗（h3） | **253/253 = 100%** |
| 程序 | 12pt 加粗 + 深红 | 232/233 = 99.6%（1 个是同名异写"冯·诺依曼/冯·诺伊曼"） |
| 专长 | 14pt 加粗 + 棕色 `rgb(118,45,0)` | 正文页 646/646 = **100%**；「种族专长」158 条只有 85 条可定位（见 §3.4） |
| 魔法物品 | 14pt 加粗 + 棕色（套装成员为 16pt 加粗） | **1585/1585 = 100%**（两套样式规则分别覆盖；此前按单一棕色口径只到 92.1%） |
| 怪物 | 18–20pt 加粗 + 黑色 | 662/679 = 97.5%（缺 11 个"毛绒动物·X"变体 + 6 个"XXX，称号"式名字） |
| 职业/种族/子职 | 页级 h1 | 一页一词条，**不需要锚点**，链接到页顶 |

**关键实现细节**：有少量（实测约 1%）的标题段落被 Word 并进了上一段（名字和上一段正文在同一个 `<p>` 里、靠 `<br>` 分隔），所以**不能只按"段落首行 = 词条名"判定**，要按"块内文本 + 每字符的 bold/size/color 样式栈"定位（脚本 `_analyze-anchor-runs.mjs` 已实测该做法可行，覆盖率见上表）。定位到后，在名字前插一个空 `<a id="kw-...">` 即可，**不需要改标题 DOM**。

**需要"兜底清单"的只有 91 条**：40 条整段文字名（脏数据）+ 33 条种族专长（标题结构不同）+ 17 条特殊怪物 + 1 条程序异写。其中大多数本来也该从关键词索引里排除（§3.4），真正要人工处理的只有几十条。

### 3.3 歧义与误链：2 字名是最大风险

- **同名 52 组**：15 组跨类别（狂野生长=法术+战技、元素武器=法术+魔法物品、震荡波=战技+程序……），3 组同名同页（锚点 id 必须加序号）。
- **≤2 字的名字 496 个**（canonName 归一后按类别重复计数；唯一名 487 个），其中按类别出现：法术 78、战技 71、程序 41、专长 54、魔法物品 85、怪物 99、职业 5、种族 28、子职 31。
- 其中"通用词"占比很高，是误链灾难：**"创造"（子职，非本页命中 1913 次）、"灵魂"（881）、"法师"（735）、"野兽"（609）、"死灵"（633）、"人类"（405）、"精灵"（285）**；另有 1 字名 **9 个**（"干""戚""蜚""蜃""件""雕""狼""猿""象"——"件"就命中 7,038 次，明显是解析残留）。
- 还有 **507 对"短名是长名子串"（涉及 229 个短名）**：如「魔能爆 / 真正的魔能爆」「法师之手 / 真·法师之手」「疗伤术 / 群体疗伤术」——最长匹配可以解决"长名优先"，但**短名出现在非词条长词里**（如"奇术"出现在"传奇术"里）无法自动区分。
- **结论**：2 字名不能"一刀切全开/全关"，需要"默认关 + 白名单人工过一遍"。496 个名单按命中频次排序后人工过一遍约 **1 小时**；法术/战技/程序的 2 字名（189 个）相对安全，可优先审。

### 3.4 数据质量地雷（不先修，加链会出丑）

| 问题 | 数量 | 例子 | 处理 |
|---|---|---|---|
| 法术名带"英文半截/斜杠/换行" | 18 | `翠炎剑Green-`、`目盲／耳聋术Blindness/`、`炎缚徽记Flamebound Symbol\n二环 变化` | 修 `parseSpells` 的英文剥离正则（改为从标题 run 取中文部分），或关键词侧用 `canonName()` 归一 |
| 专长名是整段话 | 40（全是"种族专长"） | `强健体格。在决定你的载重、和你可以推、拉及抬的重量时，你视作为体型大一级的生物` | 不纳入关键词；顺手修 `parseRaces` 的种族专长切分 |
| "种族专长"标题结构与正文专长不同 | 33 | 种族页里的 `属性值加成。你的力量+2`、`体型。山丘巨人为大型` | 不纳入关键词（或单独锚到种族页对应段落） |
| 1 字名 | 9 | `干`、`戚`、`蜚`、`蜃`、`件`、`雕`、`狼`、`猿`、`象` | 从关键词索引排除（锚点保留不碍事） |
| "XXX，称号"式怪物名 | 6 | `贝拉希拉，众目之王`、`迪恩，思维窃取者` | 同上，锚点兜底到页/段 |
| 同名同页（锚点 id 冲突） | 3 组 | `灵马哨笛·赤兔马` 等 | 锚点 id 追加 `-2`；关键词取 priority 最高者 |

### 3.5 "脏页"清单（必须排除，否则一页就几百条链接）

| 页面 | 候选（全部命中） | 其中 ≥3 字且每页首现 | 原因 |
|---|---|---|---|
| `基础/版本更新.htm` | 4,028 | **2,178** | 版本更新历史，逐条列旧内容，链上就是纯噪声 |
| `装备/魔法物品/套装.htm` | 1,063 | 379 | 套装清单 + 成员说明，链接粒度太碎（是否排除可选） |
| `法术/召唤物.htm` | 708 | 159 | 召唤物汇总长表 |
| `基础/设计师访谈.htm` | 113 | 27 | 非规则正文 |
| `基础/5z说明.htm` | 8 | 3 | 非规则正文 |
| `$$unsavedpage1/2.htm` | — | — | Word 残留垃圾页 |

> 前 4 个脏页（版本更新/召唤物/设计师访谈/5z说明）在策略里的影响：**排除它们正好省掉 2,367 条链接**（23,516 → 21,149），其中版本更新一页就占 2,178。
> 建议在 `keyword-config.json` 里维护 `excludePages`（默认上面 5 个左右），并允许按目录排除（如「私货，未通过的」是否要链，需用户拍板 §9 Q7）。

### 3.6 对既有功能的相互影响（已核对）

- **全站搜索**：索引从 `5z_src` 原文提取（`build.mjs` 409–431），加链只改 `5z_web` 产物 → 不受影响。
- **页内搜索高亮**：`HL_SCRIPT` 用 TreeWalker 走文本节点，`<mark>` 套在 `<a>` 里是合法的；清除时 `body.normalize()` 不会破坏 `<a>` → 仍可用（跨链接边界的短语会少命中，属可接受副作用）。
- **iframe 导航**：跨页锚点链接 = iframe 正常导航 → 触发 `load` → 面包屑/目录会更新，**前提是先修掉 `app.js` 不剥 `#` 的问题**（`app.js` 的 `iframe load` 处理器里 `cur.slice(base.length).split('?')[0]` → 改成先剥 `#`；否则 `urlToNode` 查不到、TOC 不高亮）。
- **缓存**：正文页 HTML 由 Cloudflare Function 设 no-cache → 改完立刻生效；但 `body.css` 的 `<link>` 没带 `?v=`（`build.mjs:363`），而 `_headers` 给 `/assets/*` 配了 1 年缓存 → **新增的链接样式对回访用户可能半年不生效**。必须给正文页的 `body.css` 也加 `?v=<buildTs>`（顺手把 `buildTs` 的计算提前到内容生成之前）。
- **旧版规则书**：`/v/<版本>/` 是 Git 历史快照反向代理，旧快照里没有链接/锚点，属预期，互不影响。
- **词典/车卡/计算器**：只要 `card-data` 只**新增** `anchor` 字段、`url` 保持原样，骰子机器人构建脚本的逐字段兼容门禁不受影响（`url` 加 `#` 才有兼容风险，故不建议直接改 `url`）。

## 5. 推荐方案设计（构建期静态注入）

### 5.1 数据流改造

```
现状：
  5z_src(Word HTML) ──build.mjs 第4步──> 5z_web 正文页（无锚点/无内链）
                    └─build.mjs 第7.5步─> parse-card-data → card-data/*.json → card-data.js → dict/car
改造后：
  5z_src ─┬─ parse-card-data（提前到内容生成之前）
          │     ├─ 原 9 类 JSON
          │     └─ 新增 anchor 字段（每个多词条目标页上的词条 → "kw-xxx"）
          ├─ linkify.mjs：读 card-data + keyword-config.json → 关键词 registry
          └─ build.mjs 第4步（processHtml）：
                ① 给本页词条标题注入 <a id="kw-xxx">
                ② 按 registry 给正文匹配处注入 <a class="wz-kw" href="目标页#锚点">
  产出：5z_web（正文页带锚点+内链；JSON 带 anchor；dict 原文链接精确）
        └─ 现有 sync-web/门禁/发布链路不变（check-links 增加 fragment 校验）
```

| `5z_build/build.mjs`（355–407 / 527–557 行） | 把第 7.5 步的 `parse-card-data` spawn **前移**到第 4 步之前（改成一个 `prepareCardData()`，7.5 只保留合并）；`processHtml()` 里接 `anchorize()` + `linkify()`；363 行 `body.css` 加 `?v=${buildTs}`（`buildTs` 计算提前） |
| `5z_build/linkify.mjs`（新） | 关键词 registry 构建、最长匹配、每页首现、排除规则、HTML 注入、统计报告 |

| `5z_build/changelog.json` + `README.md` | 发布记录与新功能说明 |

### 5.2 关键词索引（registry）的数据结构

```jsonc
// 由 card-data 自动生成（不手写），再叠加 keyword-config 的人工规则
{
  "name": "火球术",          // 用于正文匹配（canonName 归一后）
  "display": "火球术",        // 链接文字（可与 name 不同，留扩展）
  "cat": "spell",            // spell | maneuver | program | feat | magicItem | monster | class | race | subclass | term
  "target": "法术/法术详述/3环.htm",
  "anchor": "kw-火球术",      // 页级词条为 ""
  "priority": 100,           // 同名冲突时取高（法术 > 战技 > 专长/物品 > 怪物 …）
  "match": "exact",          // exact（中文名）| latin（英文名，需词边界）
  "enabled": true
}
```

- **数据源**：`assets/card-data/*.json`（构建时同一份）+ 少量人工文件：
  - 2 字名白名单/黑名单
  - 别名（如 `目盲／耳聋术` 的几种写法；怪物"XXX，称号"的短名）
  - 同名词条优先级
- **不做的事**：不引入分词器（中文名词无空格，最长匹配 + 人工名单比 NLP 更可控）；不链英文名（中文正文里英文别名只出现在标题里，链它没有意义）。

### 5.3 匹配规则（定稿建议）

1. **最长匹配优先**：先长后短，"火球术"优先于"火球"；"群体疗伤术"优先于"疗伤术"。
2. **每页每词条只链首次**（策略 D）：同一页同一关键词最多 1 条链接。
3. **名字门槛**：默认 `len >= 3`；2 字名仅白名单开启；1 字名一律不链（只保留锚点）。
4. **跳过范围**：`<script>/<style>/<head>`、已有 `<a>`、注入的 `wz-nav` 导航条、被注入的标题本身（自己不链自己）、`excludePages` 整页跳过。
5. **同名消歧**：`priority` 高者胜（法术 > 战技 > 程序 > 专长 > 魔法物品 > 怪物 > 职业/种族/子职）；同名同页的锚点 id 追加 `-2`。
6. **块内拼接**：Word 的行内标签会把词拆开（抽样 0–1.4% 的命中跨标签），所以匹配在"整块文本（`<p>`/`<td>` 内去标签拼接）"上做，注入时按字符 → run 的映射落回原 HTML，**保证不破坏原有字体/颜色/缩进**。

### 5.4 锚点方案

- **id 命名**：`kw-<canonName>`（可读、可调试、复制链接可懂）；同页重复加 `-2`；只保证页内唯一。
- **插入方式**：在标题名字文本前插 `<a id="kw-xxx"></a>`（空锚点），不动原有 `<b>/<span>` 结构。
- **页级词条**（职业/种族/子职/部分单条专长）：`anchor = ""`，链接到目标页本身。
- **兜底**（91 条）：优先"锚到该页最近的上一个标题"（例如套装成员 → 套装名），否则"页顶"；这份兜底清单写进 `keyword-config.json` 一次定死，构建门禁要求**没有词条落在"无目标"状态**。
- **稳定性**：锚点由产物重新计算，不承诺外部永久链接；跨版本改名导致的锚点变化可接受（词典链接每次构建重新生成）。若要做"可分享词条链接"，再讨论稳定 id（如拼音/序号）。

### 5.5 生成的 HTML 长什么样

```html
<!-- 目标页：法术/法术详述/3环.htm -->
<p class=MsoNormal ...><b><span style="...color:rgb(128,0,0);font-weight:bold;...">
  <a id="kw-火球术"></a><font>火球术</font><font>Fireball</font></span></b></p>

<!-- 来源页：任意正文 -->
<p ...>你对目标区域释放
  <a class="wz-kw" href="../../法术/法术详述/3环.htm#kw-火球术" title="法术 · 三环塑能">火球术</a>，
  造成 8d6 火焰伤害……</p>
```

- 同页跳转：`href="#kw-加速术"`（不触发 iframe 重新加载，瞬间定位）。
- 跨页跳转：相对路径（复用 `build.mjs` 的 `relPath`），iframe 内导航，`app.js` 修复后目录/面包屑同步。
- `title` 提供"类别 · 环位学派"等上下文，鼠标悬停即可区分同名（如 法术 元素武器 vs 魔法物品 元素武器）。

### 5.6 与壳（iframe）的联动清单

| 场景 | 现状 | 需要改 |
|---|---|---|
| 正文页内跳锚点 | 浏览器原生滚动 | 无 |
| 正文跨页跳锚点 | iframe 导航，`load` 里 `highlight(rel)` 会因 `#` 查不到节点 | `app.js` 剥 `#`（1 行） |
| 更深链接（分享"当前页/锚点"） | 壳 URL 从不变化（现在也没有） | 不在本期范围；可选 P3 |
| 从词典新窗口开"原文#锚点" | 原生支持（`target=_blank`） | 只需锚点存在 |
| 词典深链（`dict.html#spell/火球术`） | 不支持 | P2（复用 Picker 的 `state.sel` + `initialDetail`，约 0.5 天） |

### 5.7 词典侧（顺手的大收益）

P0 把 `dict.js` 六处"规则书原文"改成 `url + '#' + anchor` 后：**1,196 个法术的原文链接从"跳页顶"变成"跳到词条"**，197 个多词条页全部受益。这属于独立可上线的价值，不需要等 P1。

### 5.8 样式与可访问性

- 视觉：`a.wz-kw{ color:inherit; text-decoration:underline dotted rgba(124,58,237,.55); text-underline-offset:2px }`；hover/focus 加实线+浅紫背景；**不改变字号字色**，不打断阅读。
- 深色模式：用 CSS 变量（站点已有 `prefers-color-scheme` 适配）。
- 打印：`@media print { a.wz-kw{ text-decoration:none; color:inherit } }`（避免纸面满页下划线）。
- 跳转落点：`:target` 或页面加载脚本给目标标题加 1.2s 的浅黄闪一下（可选，提升"点到了"的确定感）。
- 键盘：链接原生可 Tab；`title` 提供上下文。

### 5.9 可选 P2：真正的"书后索引"页

用户需求名是"超链接索引"，如果字面想要一张索引页，可由 linkify 阶段顺带产出：

- `索引.html`：按类别/拼音排序列出全部关键词，每条 → 词条锚点；再列"出现在哪些页"（反向链接，linkify 时顺带统计）。
- 数据：`assets/kw-index.json`（词条 + 目标 + 出现页列表）。
- 与词典的分工：词典是"浏览/筛选/详情"，索引页是"从词找位置"的书式索引；二选一或都做由用户定（§9 Q5）。

4. **交互**：CDP 测试——点关键词后 iframe 目标标题进入视口、面包屑与目录同步、同页/跨页都对；手机视口点击可命中（触控目标不重叠）。
5. **回归**：全站搜索、页内搜索（高亮/计数/Alt↑↓）、目录展开/记忆、深色模式、打印预览、dict/car/calculator、旧版规则书入口、`card-data` 字段兼容（新增字段不破坏骰子门禁）。
6. **体积**：单页 HTML 增量 ≤8%（或 ≤60 KB）；全站 HTML 增量 ≤3 MB。
7. **发布**：更新日志新增一条（含"关键词索引/锚点"说明），README 功能列表更新。

### 10.4 名词约定

- **锚点（anchor）**：页面内一个可被 `#id` 定位的标记；本方案为每个多词条目标页的词条标题插一个空 `<a id>`。
- **首现策略**：同一页内、同一关键词只把第一次出现标成链接，避免同页满屏重复链接。
- **canonName 归一**：去掉词条名尾部的英文别名/标点（"火球术Fireball" → "火球术"），中文正文匹配用归一后的名字。
- **run 级样式判定**：按 HTML 标签栈逐字符追踪加粗/字号/颜色，判断一段文字是否"标题样式"，用于在 Word 导出 HTML 里定位词条标题。
