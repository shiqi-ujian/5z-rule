# 评估：为什么规则书是 CHM，能不能转成 wiki 那样的格式

- 日期：2026-10-26
- 需求原话：「为什么这个规则书要用 chm 格式呢，能不能转换成 wiki 那样的格式呢？」
- 结论状态：**可行，但要先区分「wiki 外观/组织」与「wiki 平台/可编辑」两件事；建议先做阅读侧的词条化，不建议直接上可编辑 wiki 平台。**
- 本文所有数字均为 2026-10-26 对 1.63 版实测（脚本见 §7）。

---

## 0. 一句话结论

1. **CHM 不是这本书的"内容格式"，是作者的"发布容器"**。真身是 WPS/Word 文档 → 另存为 HTML → 用 HTML Help Workshop 4.1 打包成 .chm；作者选它是因为「单文件分发 + 自带目录/索引/全文搜索 + Windows 双击即读 + 不用租服务器」，对单作者发布版本最省事。
2. **能转成 wiki 形态，而且这个站点已经完成了大半**：661 页正文、4,571 个词条锚点、15,063 条关键词互链、10MB 全站搜索索引、4 个历史版本存档都在；离「wiki 那样」主要差三件事：**一页一词条的 URL 粒度、反向链接（谁引用了我）、分类/标签页**。
3. **不建议直接上 MediaWiki/Wiki.js 这种可编辑 wiki**：规则书是鬼方朱雀用 WPS/Word 写完、按版本（1.49→1.63）整包发布的；wiki 一旦成为第二份内容源，下一版 CHM 一到，社区的修改就会被覆盖或需要人工合并——这是**内容主权问题，不是格式问题**。除非作者本人搬到 wiki 写作，否则性价比很低。
4. 若目标是给外部 wiki 搬站（灰机/Fandom/自建），**可以一次性导出 Markdown/MediaWiki 语料**：试点已验证正文保真 98.9%–100%，但表格、标题、手打列表需要规则 + 人工抽检（详见 §5）。

## 2. 作者为什么选 CHM（而不是网页/wiki）

| 需求 | CHM 给的 | wiki 需要 |
|---|---|---|
| 单文件分发（QQ 群文件/网盘，17.8MB） | ✅ 一个文件 | ❌ 需要站点 |
| 离线可读、双击即开 | ✅ Windows 自带 hh.exe | ❌ 需要浏览器 + 联网 |
| 目录树 / 关键词索引 / 全文搜索 | ✅ 编译时白送（693 节目录、658 条索引、`$FIftiMain` 全文索引） | 需要自己建 |
| 版本发布（1.60/1.61/1.62/1.63 整包替换） | ✅ 天然符合 | ❌ 与"持续编辑"模式冲突 |
| 防误改、防脚本 | ✅ 相对安全 | ❌ 要权限/审核/防破坏 |
| 作者零运维 | ✅ 无服务器 | ❌ 域名/部署/备份/升级 |

所以 CHM 对**单作者、按版本发布、离线分发**这个场景是合理选择；它的代价全部由下游（也就是这个项目）承担：

## 3. CHM 作为「源格式」的代价（1.63 实测）

| 指标 | 数值 | 意味着什么 |
|---|---|---|
| 正文页 | 661 个 `.htm` | 页面粒度＝章节/分类页，不是词条页 |
| HTML 体积 | 122.1 MB | Word 导出垃圾极重 |
| 正文字符 | 3,864,768 字 | **HTML : 正文 ≈ 33 : 1** |
| `<p>` / `<span>` / `<o:p>` | 137,998 / 331,113 / 140,662 | 无 `ul/ol/li`（列表是手打编号的段落） |

| 语义标题 | 仅 258 页有 `h2`(167)/`h4`(2,567)，其余是「样式加粗」段落 | 不能直接按 HTML 结构转 wiki |
| 正文内链 / 锚点 | **17 条 `<a>`（全是外链/附件/坏 `#`）、0 个 `id`/`name`** | 原书没有超文本，只有"书" |

## 4. 这个项目离 wiki 有多近（已有资产）

| 维度 | 现状 | 距 wiki 差什么 |
|---|---|---|
| 页面 | 662 页静态站 + 左侧目录树 + 面包屑 + 上下页 | 缺「一词条一 URL」 |
| 搜索 | 10.5MB 倒排索引（BM25、交集/并集/短语/分类过滤） | 缺「词条直达」（已有锚点，可补） |
| 互链 | 4,571 个子词条锚点（`#kw-*`）+ 15,063 条正文自动互链 | 缺**反向链接**（"哪些页面引用了火球术"）、缺分类页 |
| 词条数据 | 9 类 5,014 条（法术 1,196 / 专长 804 / 魔法物品 1,585 / 怪物 679 / 战技 253 / 程序 233…），其中 1.51M 字全文（≈全书 39%） | 词条数据已可直接生成独立页面（词典弹窗 → 独立页） |
| 历史 | 「旧版规则书」按 git 提交反代 4 个历史版本（零存储） | 缺**词条级历史**（可复用同一机制） |
| 反馈 | 问题收集（腾讯文档桥 → inbox/done）+ 更新日志公示 | 缺「页内编辑/提案」入口（可接 Issues/PR） |
| 词典 | 5,014 词条可浏览/搜索/筛选，「📖 原文」已精确到锚点 | 缺「词条页 / 分类页 / 反链」 |

> 也就是说：**数据层已经 wiki 化，渲染层还是"书"**。把词典的条目详情从弹窗升级成独立页面，再补反链和分类，观感就是标准 wiki。

## 5. 试点：HTML → Markdown 实测（验证"能不能导出成 wiki 语料"）

脚本：`5z_build/调研/_pilot-wiki/convert.mjs`（自研、零依赖；运行 `node 5z_build/调研/_pilot-wiki/convert.mjs`）
产物：`5z_build/调研/_pilot-wiki/out/`（5 页样本，含 front matter：title/source/book）

| 页面 | 文本保留 | 标题恢复 | 表格 | 名单 |
|---|---|---|---|---|
| 基础/掷骰.htm（纯散文） | 99.9% | 6 | 0 | — |
| 职业/法师/原初魔力.htm | 100.0% | 1 | 1（HTML 兜底） | — |
| 法术/法术详述/3环.htm（155 法术） | 98.9% | 156 | 1 | 155/155 ✅ |
| 装备/魔法物品/武器/武器（近战）.htm（182 物品） | 99.2% | 152（原始规则 194） | 3 | 152/182（h4 误用正文，见下） |
| 怪物/不死生物/亡灵（CR0-7）.htm（8 怪） | 99.0% | 8 | 0 | 8/8 ✅ |

**已跑通的做法**：复用 `lib/anchorize.mjs` 的颜色口径（法术/程序 12pt 加粗 `rgb(128,0,0)`、专长/物品 14pt 加粗 `rgb(118,45,0)`、怪物 ≥18pt）把「样式标题」还原成 Markdown 标题；Word 表格 → HTML 表兜底；`&nbsp;`/实体解码、首行缩进剥离、`****` 清理。

**必须处理的问题清单**（也是"人工抽检"的成本来源）：

1. **`h4` 被作者当正文段用**：例如武器页把物品描述写成 `<h4>`，纯按标签转会把正文变成标题（试点已加"长句降级"规则，但会误伤 22/182 个真标题）。
2. **标题约 1% 并进上一段**（超链接索引分析已实测）→ 转换后需按样式 run 再切。
3. **手打编号列表**（`1、` / `•` 写在正文里，`mso-list` 标记仅 221 处/47 页）→ Markdown 列表化只能启发式，人工校对。
4. **表格无 `<th>`、含 `colspan/rowspan`** → 转 GFM 表会丢结构，试点全部走 HTML 表（Markdown/MediaWiki 都能渲染）。
5. **图片路径**（`xxx.files/image001.png`）→ 需重映射到 `assets/` 并保留 11 张图。
6. **`基础/版本更新.htm`（5MB/137 表）** 不适合搬，单独排除。
7. **Word 的 33:1 垃圾**：122MB → 按试点压缩比推算 Markdown 全量约 13–16MB（试点 5 页：源 2.29MB → 303KB，≈7.7:1）。

**结论**：导出 Markdown 技术上没有拦路虎，但"全量 661 页一次性搬完且零人工"不现实；合理预期是**脚本 95% + 抽检/修 5%**。

## 6. 路线对比

| 路线 | 产物 | 服务器 | 工作量 | 风险 | 适合 |
|---|---|---|---|---|---|
| **A. 词条化阅读 wiki（推荐）** | 现有站新增 `/entry/<词条>` 页（含数据卡/全文/反链/分类/原文锚点），词典详情升级为独立页 | 无 | 2–4 天 | 低（纯新增，不改发布链） | 读者/群友查词条、喂骰子机器人 |
| **B. Markdown/MediaWiki 语料导出** | 661 页 `.md` 或 MediaWiki XML 包 | 无 | 3–5 天一次性 | 中（标题/表格需抽检；每版需重跑） | 搬到灰机/Fandom/自建 wiki |
| **C. 真·可编辑 wiki**（MediaWiki/Wiki.js/Outline） | 独立实例 + 账号/权限/备份 | **需要** | 1 周 + 长期运维 | **高**：内容主权（见 §0.3）、版权（书自述大量搬运 D&D 5e/3e 等）、防滥用 | 只有作者同意把写作搬到 wiki 时 |
| **D. 现状 + 零散 wiki 特性** | 反链、分类页、词条永久链接、GitHub 编辑入口 | 无 | 1–3 天 | 极低 | 先小步验证 |

**推荐顺序**：A（=D 的完整版）→ 需要外部镜像再做 B → C 除非作者拍板否则不做。

### 为什么 C 不划算（展开）

- **内容主权**：作者每版用 WPS/Word 重出整本，我们的站点是"发布物镜像"；wiki 的第二份内容没有回流通道。历史上（1.60→1.63）版本间隔约 1–2 个月，社区改的东西下版必冲突。
- **版权**：`基础/5z说明.htm` 明确写"大约一半是原创，另一半是搬运（和抄袭）"，来源包括 D&D 5e/3e、Pathfinder、网络文学、游戏等。公开可编辑 wiki 会放大版权风险；现在的「只读镜像 + 反馈收集」更稳。
- **协作价值有限**：贡献者（永生之眼、琉璃 official、移动宝箱、约翰娜…）已经在 QQ 群/论坛投稿，作者自己整合进下一版——相当于有人工 wiki 流程，只是没有 wiki 界面。
- **运维**：MediaWiki 要 PHP+DB、升级、防 spam；Wiki.js 要 Node+DB+账号体系；对一个人维护的项目是净负担。

### 8.2 规律（这几条比"选哪个格式"更重要）

1. **CHM 是「离线整包发布」的历史习惯，不是技术优势**。中文圈三个典型（5E不全书、無限恐怖、5z）都是「Word/WPS/WinCHM 的 HTML → CHM」，按版本整包发（QQ 群 / GitHub Release / 网盘），共同缺点是手机打不开、无内链、体积大；5E不全书的 README 自己就写了"手机/非 Windows 需要特殊查看器"。
2. **wiki 承担的是「可检索的百科 + 翻译协作」，不是「规则书正本」**。灰机 DND wiki、HKTRPG、PathfinderWiki、dandwiki 全是 MediaWiki；但它们的内容要么来自数据站，要么来自 CHM 项目（灰机明确写译文来自 5E不全书/纯美苹果园）。**作者不在 wiki 上写正本**。
3. **成熟项目已经收敛到「一份源 → 多端产物」**：5E不全书用 `wcp2web` 从同一份 HTML 源同时产 CHM + Web + 搜索索引（GitHub Actions 自动发布）；5thsrd 用 MkDocs + Git；5etools 用 JSON 数据 + 静态站；Pathfinder 用「数据库站（规则）+ wiki（百科）」分工。**CHM 只是其中一个出口，不是源。**
4. **「规则正本放可编辑 wiki」在中文 TRPG 圈基本没有成功案例**。原因：版本化发布（一版一包）、版权（OGL/CC/非官方翻译）、翻译质量把关（灰机也要靠共库+人工校对）。真正社区化的只有「百科/索引/术语」，不是规则正文。
5. **5z 的位置**：内容形态最像 5E不全书（CHM 上游 + 自建 Web），但多了词典/车卡器/版本存档；缺 5E不全书 的「自动 Web 构建 + 服务端搜索」和灰机 的「词条页/反链/编辑协作」。**结论不变：做阅读侧词条化（路线 A）性价比最高，CHM 继续当上游发布物。**

### 8.3 如果照抄一个对象，抄谁？

| 目标 | 抄谁 | 抄什么 | 不抄什么 |
|---|---|---|---|
| 让手机/在线读者好用 | 5E不全书 | `源码 → 自动构建 Web + 搜索索引` 的流水线（GitHub Actions） | 它的 WinCHM 编辑流程（我们上游是作者 CHM） |
| 让词条可检索、有反链/分类 | 灰机 wiki | 一页一词条 + 分类 + 反向链接 + 编辑历史 | 它的编辑门槛/平台绑定/版权口径 |
| 让工具/骰子直接用数据 | 5etools 中文站 | 数据卡单一数据源（我们已有 card-data） | 它的前端复杂度 |
| 让规则稳定可离线 | 5thsrd / 5E不全书 | 每次发布附「离线包」（我们可直接给整站 zip） | — |

## 9. 待拍板问题

1. 你要的「wiki 那样」是 **读起来像 wiki**（词条页/互链/反链/分类），还是 **能编辑**（账号、协作、历史）？
2. 要不要**对外导出**一份 Markdown/MediaWiki 包（给别人搬站/存档）？
3. 词条页的 URL 形态：`/entry/火球术/`（真静态页，SEO/分享好）还是 `dict.html#spell-火球术`（改动最小）？
4. 是否接受「词条页与规则书页并存」（同一内容两个入口，靠 canonical/面包屑指回规则书原文）？
