# 5z 规则站 问题处理维护手册（Agent SOP）

> 本手册是 agent 每次被定时唤醒后的处理规程。唤醒源：dsh-schedule 每 60 分钟持久提醒（2026-08-17 起，原 10 分钟）。
> 相关路径均相对仓库根 `E:\5z-rule`。

## 0. 职责

群友通过腾讯文档收集表（链接发 QQ 群）提交问题 → 系统定时读取到 `问题收集/inbox/` → 本 agent 自动 debug、修复、发布到 GitHub Pages，并把结果写入网站「更新日志」页公示。

**安全铁律（违反即事故）**：
- `问题收集/`、`5z_build/feedback-bridge/config.json`、`docs-profile/`、`feedback-state.json` 都已在 .gitignore 中，**严禁** `git add` 或提交其中任何内容（公开仓库）。
- 推送前必须 `git status --short` 检查变更清单，确认无敏感文件。
- 网站内容是整体重建的：**修复必须落在源（5z_src 片段或 5z_build 模板/工具链），绝不手改根目录生成物**（重建会被覆盖）。

## 1. 每轮处理流程

1. **读告警**：检查 `问题收集/alerts.md`（读取桥写入的告警）。有内容 → 先处理（如提示用户重新登录），处理完清空该文件。
2. **读取收集表**：运行 `node 5z_build/feedback-bridge/collect-docs.mjs`（或确认读取桥/手动导入已把新问题放进 `问题收集/inbox/`）。
3. **列出 inbox**：`问题收集/inbox/*.json` 全部为待处理。无新问题 → 一句话结束本轮，不输出长文。
4. **逐条处理**（见第 2、3 节）：
   - 能定位并安全修复 → 修复 + 校验 → 计入本批发布。
   - 无法复现 / 描述不清 → `status: "need-info"`，在 `resolution` 写明缺什么信息，记入 changelog 的 pending 列表公示。
   - 需要用户决策 → `status: "blocked"`，在会话里说明并留待用户处理。
5. **发布**（本批有修复时）：见第 4 节。
6. **更新日志**：见第 5 节。
7. **收尾**：处理完的 inbox 文件移入 `问题收集/done/`（保留原 JSON，`status` 更新为 done，`resolution`/`released`/`doneAt` 填好）。

## 2. 修复来源定位表

| 问题类型 | 修复位置（源） | 说明 |
|---|---|---|
| 规则内容错误（法术/职业/怪物/装备…数值或文案） | `5z_src/<分类>/<页面>.htm`（如 `5z_src/法术/火球术.htm`） | 重建会整体再生成，必须改这里 |
| 词典/车卡/搜索等网页功能 bug | `5z_build/` 模板：`car.html`、`dict.html`、`shell.html`；数据解析 `parse-card-data.mjs` | 模板 → 重建后同步到根目录 |
| 站点整体样式/交互（index 壳） | `5z_build/shell.html`、`assets/site.css`、`assets/app.js`（在 `5z_build/assets/`） | 同左 |
| 构建/检查工具 bug | `5z_build/build.mjs`、`check-links.mjs`、`verify-complete.mjs`、`sync-web.mjs`、`update.mjs` | 改动后务必 `--dry-run` 演练再发布 |
| 更新日志页本身 | `5z_build/changelog.json` + `gen-changelog.mjs` | 见第 5 节 |

定位辅助：先在根目录（发布后的站点）复现/核对问题，再反查 `5z_src/` 或 `5z_build/` 中的对应源。

## 3. 校验

- JS 语法：`node --check <文件>`
- 搜索/数据回归：`node 5z_build/test-search.mjs`（若存在）
- 构建期检查（发布流程自带）：链接完整性 `check-links.mjs`、页面完整性 `verify-complete.mjs`
- 页面交互验证：参照 `5z_build/_test-*.mjs` 的无头 Edge CDP 模式写临时验证脚本（文件名以 `_test-` 开头，gitignore 已忽略），截图到 `5z_build/_shots/` 自查
- 内容页改动后：可在本地起静态服务（`5z_build/_test-serve.mjs` 模式）人工核对渲染

## 4. 发布

```bash
node 5z_build/update.mjs --no-extract --message "fix: 修复 <问题id> <标题>（若为多问题批量：fix: 修复反馈问题 <ids>）"
```

- `--no-extract`：用现有 `5z_src` 重建（不碰 CHM）。**没有新 CHM 时不能去掉该参数。**
- 流程自动：构建 → 链接/完整性检查（失败即中止，**不推送半成品**）→ 同步根目录 → `git add -A` → commit → push → GitHub Pages 上线。
- 发布前先 `git status --short` 检查变更清单。
- 若某问题需单独验证但同批还有其他修复：全部修完再一次性发布，changelog 一次性记录。
- 构建失败：读 `update.mjs` 报错定位；不要反复重试同一失败，先查明原因。
- 推送失败（代理/网络）：git 配置了本地代理（`git config http.proxy`）。失败时先重试一次；再失败则临时绕过代理推送 `git -c http.proxy= -c https.proxy= push`（不修改全局配置）；仍失败则保留本地提交，在会话中提示用户代理状态，下次巡检时先 `git status` 检查未推送提交再补推。

## 5. 更新日志维护

1. 编辑 `5z_build/changelog.json`：在本批对应 entry 的 `fixes` 追加 `{id, title, detail, page}`；无法处理的追加到 `pending` `{id, title, note}`；如跨天可新建 entry。
2. 页面在每次构建时自动生成（build.mjs 调用 gen-changelog.mjs → `5z_web/更新日志.html` → sync 同步到根目录发布源）；无需手动运行。手动预览可用 `node 5z_build/gen-changelog.mjs 5z_web`。
3. 页面由 `git add -A` 一并提交（update.mjs 第 5 步），随发布上线。

## 6. 特殊情形

- **读取桥告警（alerts.md 有内容）**：通常是未登录或页面结构变化 → 提示用户运行 `5z_build/feedback-bridge/login-docs.bat` 重新登录，或 `collect-docs.mjs --probe` 后根据输出校准提取逻辑；期间可继续处理已入库问题。
- **5z_src 缺失/无法重建**：内容类修复无法发布 → 记录并提示用户恢复 5z_src（可重新反编译 CHM）；网页/工具类修复不受影响仍可发布。
- **表单截图附件**：读取桥尽力下载到 `问题收集/attachments/<id>/`，缺失时按描述判断即可。
- **重复问题**：读取桥按内容哈希去重；处理时若发现与 done 中问题重复，合并并注明。

## 7. 运行前提（提醒用户）

- Harness 服务运行中，且本会话保持打开（schedule 到期才能准时唤醒；关闭期间到期项会在重开后补处理）。
- 读取桥登录态有效（定期用 `login-docs.bat` 刷新）。
- Node.js、git 凭据可用（`一键更新.bat` 已验证）。
